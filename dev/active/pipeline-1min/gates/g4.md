- Seconds come from server-side `pipeline.timing`. Where n = 2 the cell shows the median, then the runs as (r1 / r2).

- Columns:
  - **prod v8** = cold reference, `g0-prod-baseline.md` + `.json`.

  the first tab was the first extracted tab.
- Extraction wall: in v8 this is the single call. In v9 it is the longest group call. A visual group starts at
  frames-done.

  - Break-even: 1 write + n reads ≤ (n + 1) × uncached needs n ≥ 1.1.

  - A 5m write ($0.0611) wins as soon as one read follows within 5 minutes: $0.0611 + $0.0049 = $0.066 vs $0.0978.
    The simulation from prod arrival times decides (D26(2)).

## 9. Item 5 — media download speed (2026-10-14, local, not pushed)
**Why bF2dm1AmmQE's scene detection waited for an 88 MB file (prod v10, 11:39 UTC):** scene detection always read the
pass-1 ("low-res") file, never the 720p one — but pass 1 WAS 88 MB. Its spec `worstvideo[ext=mp4]` ran on the android
client, which serves no video-only rendition, only the muxed 360p file (format 18, audio included). The 720p download
(`web_embedded,android`) got format 18 too: YouTube's SABR experiment drops web_embedded's renditions in some sessions.
Both identical 88,476,325-byte files then downloaded side by side through the proxy (started 6.06 s); the 720p copy
landed at 73.7 s, pass 1 at 103.9 s, scene detection started at 103.9 s. Format 18 is 2–4× a 360p video-only file and
often bigger than the 720p one (MiB, format 18 / 134 / 136: bF2dm1AmmQE 84.4 / 43.6 / 118.6, jMq8 79.3 / 23.9 / 68.2,

**What changed (code):**
- `pipeline.timing.downloads` per file: `bytes`, `wallMs`, **`mbPerSec`**, and for the video downloads the picked
  `format` + `height`, `clients`, `proxyExit` ("n/m", null = direct) and a short `error` (`download_timing.py`).
- Pass 1 = the smallest ≥360p video-only rendition, H.264 first, through the video clients first (`web_embedded,android`,
  then `android`) — same 360p detection frames, 2–4× fewer bytes when YouTube serves video-only renditions; format 18
  when it doesn't (no worse than before).
- Scene detection reads the 720p download's file when it lands first as the same ≤360p rendition (the format-18 twin)
  and cancels pass 1; a real 720p file is read only when pass 1 fails.
- The hi-res pass reads the 720p file only when it is already on disk. Otherwise the 360p frames are uploaded, vision +
  OCR read them, and a deferred pass (`hires_upgrade.py`) overwrites the same S3 objects once the file lands — only
